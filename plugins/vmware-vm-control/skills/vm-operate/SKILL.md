# Operating a VMware VM with vmware-vm-control

All tools run on the host. Screen, mouse and keyboard go through the VNC server embedded in VMware (works for any guest OS, even at boot or in the BIOS). Commands, files and processes go through `vmrun` and need VMware Tools in the guest.

## Start of every session

1. Call `vm_list` to see the VMs VMware knows on this PC (refer to them by name), whether they run, and their VNC / login status.
2. If VNC is off or the login is not stored, follow the **vm-setup** skill (`vm_prepare`) instead of improvising.
3. If the VM is off, start it with `vm_power` (`action: start`) and wait for the desktop with `vm_screenshot`.

## Choosing the right tool

| Need | Prefer | Why |
|---|---|---|
| Anything scriptable (files, registry, services, installers with silent switches, reading logs) | `vm_run` | Exact, fast, returns output and exit code |
| GUI-only programs, dialogs, legacy configuration tools | `vm_screenshot` + `vm_click` / `vm_type` / `vm_key` | Works for any application |
| Moving files | `vm_copy`, `vm_files` | No network share needed |
| Risky change | `vm_snapshot` (`create`) first | Workstation/Fusion only - not Player |

## GUI loop

1. `vm_screenshot` before acting. Coordinates for `vm_click`, `vm_move`, `vm_drag` and `vm_scroll` are pixels of the **last full screenshot** of that VM; the server converts them to guest pixels.
2. Use `region` to zoom into small text (enlarged to at least 1:1, up to 4x); zoomed images do not change the click scale - take a normal screenshot again before clicking.
3. Calls answer within about 40 s: `vm_power start` may return "still in progress" while VMware opens its window - check with `vm_list` instead of starting again; `vm_guest_info` with `wait` may return "IP not available yet".
3. Pass `screenshot: true` on input tools to see the result in the same call; give slow dialogs a larger `wait`.
4. **Never type blind.** After any key or click that should open a window (Win+R, a menu, a dialog), take a screenshot and confirm that window is focused BEFORE `vm_type`. Typed text plus Enter landing on the desktop can launch shortcuts or worse. Pop-ups (activation, updates, UAC) often steal focus right after logon - close them first.
5. `vm_type` converts text for the guest keyboard layout (US, Brazilian ABNT/ABNT2; others fall back to Alt+code). It reports characters it could not type - write those with `vm_run` instead. When the layout is unknown it refuses symbols; run `vm_prepare` first.
6. Use keyboard shortcuts when they are reliable (`win+r`, `alt+f4`, `ctrl+alt+delete`, `ctrl+shift+esc`).

## Command rules

- `shell: "cmd"` works on every Windows version (XP included). Write normal batch syntax; multi-line scripts are fine.
- `shell: "powershell"` only exists on Windows 7 / 2008 R2 and newer (and XP/2003 only if PowerShell 2.0 was installed). Check with `vm_run` + `ver` when unsure.
- Programs that must appear on the user's desktop need `interactive: true` (and usually `no_wait: true`).
- Non-ASCII output is decoded as UTF-8, then CP850, then CP1252. For files, prefer `vm_copy` back to the host and read them there.

## Safety rules (always)

- Never type, request or store passwords on the user's behalf. The guest login is typed by the user in the Windows credential dialog (`vm_prepare` / `vm_credentials`); the VNC password is generated by the plugin. If a Windows login screen appears inside the VM, stop and ask the user to log in.
- Take a snapshot before installing software, changing system settings or deleting data, when the host type supports it.
- Ask the user before deleting files, killing unknown processes, changing network settings or powering off a VM that may hold unsaved work.
- Do not enable VNC without a password on a VM reachable from a network; VMware's VNC listens on all host interfaces.

## Configuration changes

For any change to the VM hardware/options or to Windows settings inside the guest, follow the **vm-configure** skill.
